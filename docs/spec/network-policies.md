# Septuvo — network, DNS and fail-closed policies (M1-02)

**Status:** requirements draft for owner review. It defines **what** must happen to packets and DNS in the version 1 journeys (D-027); it does not design the SVP protocol. Owner questions are marked **Q*n*** and collected in section 11.
**Builds on:** [threats.md](threats.md) (adversaries ADV-*, assumptions ASM-*), D-006 (every network untrusted, fail closed, explicit LAN exceptions), D-020 (four status stages) and the policy model in `crates/septuvo-policy` (N1-02).

## 1. Words used here

| Term | Meaning |
| --- | --- |
| **Underlay** | The network the device is physically attached to (Wi-Fi, Ethernet, mobile). Always hostile (ASM-08). |
| **Tunnel** | The authenticated, encrypted SVP path to the user's Septuvo Server. |
| **Protected traffic** | Traffic the policy sends to the tunnel. It goes through the tunnel or is dropped; it never goes anywhere else. |
| **Underlay exception** | The minimum traffic needed to join the underlay and reach the server (section 3). Generated by Septuvo, never by the user. |
| **LAN exception** | A destination the user explicitly approved to be reached directly, outside the tunnel (`direct` rule). |
| **Kill switch** | Firewall rules that drop protected traffic whenever the tunnel is not usable. |

Example addresses below use the documentation ranges for public addresses (RFC 5737, RFC 3849). Home network: `192.168.50.0/24` and `2001:db8:50::/64`, NAS `192.168.50.10`, home DNS `192.168.50.1`. Septuvo Server public endpoint: `203.0.113.7`, UDP. Tunnel addresses are shown as `10.99.0.x`; the real default range is **OPEN** (Q13).

## 2. Enforcement principles

| ID | Requirement |
| --- | --- |
| NP-E1 | **The firewall is the kill switch, not the routing table.** Routes steer traffic; firewall rules guarantee that protected traffic can only leave through the tunnel. Route tricks such as `0.0.0.0/1` + `128.0.0.0/1` are never counted as leak protection. |
| NP-E2 | Kill-switch rules are installed **before** the first handshake and stay installed until the user explicitly disconnects (D-019; Q2). Reconnecting, roaming and rekeying never remove them. |
| NP-E3 | Rules cover **IPv4 and IPv6** equally. If the tunnel carries no IPv6, protected IPv6 is dropped, not sent directly. |
| NP-E4 | Rules do not depend on the underlay's interface name, SSID, gateway address or subnet, so a network change cannot open a gap. |
| NP-E5 | If the Septuvo service crashes, the kernel keeps enforcing the last rules (ASM-06). On restart the service checks and repairs them before anything else. |
| NP-E6 | Every change to routes, firewall or DNS is transactional: applied completely or rolled back completely, and removable without leaving rules behind (verified in N1-03). |
| NP-E7 | No address range is trusted because it is private (RFC 1918, RFC 4193 ULA, link-local, CGNAT). Only `direct` rules bypass the tunnel. |
| NP-E8 | Policy decisions follow the N1-02 model: the most specific matching prefix wins; the same prefix twice is rejected; a `direct` rule for `0.0.0.0/0` or `::/0` is rejected; split mode must protect something. |

## 3. Underlay exceptions (the complete list)

Allowed outside the tunnel while the kill switch is active, on the underlay interface only:

| ID | Traffic | Why |
| --- | --- | --- |
| NP-U1 | DHCPv4 (UDP 67/68) and DHCPv6 (UDP 546/547) | Get an address on the underlay |
| NP-U2 | IPv6 neighbour discovery and router solicitation/advertisement (ICMPv6 types 133–137, link-local only) | Basic IPv6 operation on the link |
| NP-U3 | UDP to and from the Septuvo Server endpoint(s) only (address and port from enrollment) | The tunnel itself |
| NP-U4 | Loopback | Local software; never leaves the device |
| NP-U5 | Captive-portal mode, only when the user starts it (Q1) | Hotel and café login pages |

Anything else on the underlay is dropped unless a LAN exception allows it. DNS on the underlay is **not** an exception: the server endpoint is stored as an address at enrollment so no underlay DNS is needed (a DNS-name endpoint is **OPEN** for M2). Layer 2 traffic such as ARP is outside IP firewall scope and unaffected.

## 4. Scenarios

Each scenario states the packet path, the DNS path, where any exception comes from, what authentication is required and what happens on failure.

### NP-S1 — Journey B: untrusted Wi-Fi, full tunnel through the user's own server

- **Setup:** `mode full-tunnel`; server endpoint `203.0.113.7`; no LAN exceptions.
- **Steps:**
  1. The device joins café Wi-Fi.
  2. The kill switch is installed, or already active.
  3. DHCP and IPv6 ND run (NP-U1, NP-U2).
  4. The SVP handshake to `203.0.113.7` runs (NP-U3).
  5. The server's identity is checked against the identity pinned at enrollment.
  6. Tunnel routes for `0.0.0.0/0` and `::/0` are added.
  7. DNS is switched to the tunnel resolver.
  8. Status stages are checked one by one: adapter → authenticated peer → reachability → DNS (D-020).
- **Packet path:** app → TUN → encrypted SVP over UDP to the server → server decrypts → NAT → internet.
- **DNS path:** all queries go to a resolver reachable only through the tunnel (the server's resolver, or one the user configures behind it). DNS over UDP/TCP 53 and DNS over TLS (853) to anything else is dropped. DNS over HTTPS used by apps travels inside the tunnel like other web traffic.
- **Exception source:** underlay exceptions only (section 3).
- **Authentication:** no protected packet is sent before the server is authenticated; a wrong or unknown server identity stops the connection, with no fallback (S-01, S-05).
- **On failure:** if the handshake fails, the server is unreachable or the tunnel drops, protected traffic is dropped and the status shows which stage failed. Roaming Wi-Fi → mobile keeps the rules (NP-E4). Hostile router advertisements cannot add a bypass because the firewall, not the route, decides (NP-E1).

### NP-S2 — Journey A: reach the home network from away, split tunnel

- **Setup:** `mode split`; `tunnel 192.168.50.0/24`; `tunnel 2001:db8:50::/64`; server at home behind a port forward (R-01, Q12).
- **Packet path:** traffic to the home prefixes → TUN → SVP → home server → home LAN (only if the gateway allows this device to reach that destination, section 7). All other traffic goes directly through the café network and is **not protected by Septuvo**.
- **DNS path:** queries for the home domain(s) the user configured (for example `home.arpa`) go **only** through the tunnel to the home resolver `192.168.50.1`. Other queries use the café's DNS, like any unprotected traffic. Home-domain queries are dropped, never sent to the café DNS, while the tunnel is down (R-05).
- **Exception source:** the home prefixes come from the server's policy at enrollment; no LAN exceptions.
- **Authentication:** as NP-S1, plus the gateway's per-device authorization (section 7).
- **On failure:** traffic to the home prefixes is **dropped**, never sent into the café network, even if the café uses the same subnet (NP-S5). The UI states clearly that split mode protects only home traffic (R-03).

### NP-S3 — Journeys A and B together: full tunnel through the home server

- **Setup:** `mode full-tunnel`; the home server is also the internet exit.
- **Packet path:** home prefixes → tunnel → home LAN (authorized per section 7); everything else → tunnel → home internet connection.
- **DNS path:** everything through the tunnel, as NP-S1; the home resolver answers both home names and internet names.
- **On failure:** as NP-S1. This is the recommended default profile when the server is at home.

### NP-S4 — At home, exit elsewhere, one approved NAS reached directly

- **Setup:** the user is on the home LAN, tunnelled to a server elsewhere (for example a VPS). `mode full-tunnel`; `direct 192.168.50.10/32` approved by the user for the NAS.
- **Packet path:** NAS traffic goes directly on the LAN; every other destination, including other home devices such as `192.168.50.11`, goes through the tunnel or is dropped.
- **DNS path:** through the tunnel. The NAS is reached by address or by a name the user configured in Septuvo; local name discovery (mDNS, `.local`) is blocked by default (Q3).
- **Exception source:** the user's explicit approval, stored in the device policy and shown in status. The approval may record the network it was made on, but SSID or gateway address is **not** a security boundary (ADV-01 can copy them).
- **On failure:** if the tunnel drops, the NAS stays reachable (an approved exception) and everything else is dropped.
- **Note:** a LAN exception gives no encryption. The NAS service needs its own security (non-goal in threats.md).

### NP-S5 — Overlapping subnets

- **Situation:** the café network is `192.168.1.0/24` and the home network is also `192.168.1.0/24`.
- **Requirement:** while connected, the tunnel wins. Traffic to `192.168.1.0/24` goes to the tunnel or is dropped, and is **never** delivered to the café network. The café gateway remains usable only for the underlay exceptions (DHCP, ND) needed to stay connected. Café devices at those addresses are unreachable, which is the safe outcome (Q5).
- **Configuration conflict:** a user-approved LAN exception with the same prefix as a tunnel prefix is rejected (NP-E8); the user must choose.
- **Later option, not version 1:** presenting the home network under a different, non-overlapping prefix at the gateway (address mapping); this needs its own design in M2/M3.

## 5. IPv6

| ID | Requirement |
| --- | --- |
| NP-6.1 | Full-tunnel mode protects IPv6 exactly like IPv4. If the server has no IPv6 exit, protected IPv6 is dropped and the status says IPv6 is unavailable. |
| NP-6.2 | Router advertisements on the underlay may configure the underlay link, but cannot create a path around the kill switch (NP-E1). |
| NP-6.3 | IPv4-mapped IPv6 addresses (`::ffff:a.b.c.d`) are IPv6 and never match IPv4 exceptions (already enforced in N1-02). |
| NP-6.4 | IPv6-only underlay networks with NAT64/464XLAT reaching an IPv4-only server: support is **OPEN** (M2/M5). Until tested, the connection must fail visibly, never leak. |
| NP-6.5 | Privacy addresses and other underlay address changes behave like a network change (NP-E4). |

## 6. DNS

| ID | Requirement |
| --- | --- |
| NP-D1 | In full-tunnel mode every DNS query goes through the tunnel; DNS to any other destination on ports 53 and 853 is dropped. |
| NP-D2 | In split mode, queries for the configured home domains go only through the tunnel; with the tunnel down they fail and never go to the underlay DNS. |
| NP-D3 | The original DNS settings are restored on explicit disconnect and on uninstall, and repaired after a crash. |
| NP-D4 | The DNS status stage (D-020) is shown as working only after a real lookup through the tunnel resolver succeeds. |
| NP-D5 | DNS answers from the underlay are never used for protected destinations. |
| NP-D6 | Encrypted DNS chosen by apps (DNS over HTTPS) is ordinary traffic, protected by the tunnel in full-tunnel mode. Septuvo does not claim to control it in split mode. |

## 7. Gateway (Septuvo Server) rules

| ID | Requirement |
| --- | --- |
| NP-G1 | **An authenticated device is not an authorized destination (S-09).** The server keeps, per device, the prefixes it may reach (home LAN, internet exit or both) and drops everything else. Client-side routes are never trusted for this. |
| NP-G2 | Traffic between enrolled devices through the server is blocked unless the administrator allows it (Q6). |
| NP-G3 | Source addresses inside the tunnel must match the tunnel address assigned to that device; anything else is dropped (no spoofing between devices). |
| NP-G4 | Internet exit (journeys B and A+B) uses NAT on the server; the server's own management services are not reachable through the tunnel unless allowed. |
| NP-G5 | A revoked device's sessions are terminated and its traffic dropped immediately on that server ([identity-and-privacy.md](identity-and-privacy.md)). |

## 8. Failure and state behaviour

| Event | Required behaviour |
| --- | --- |
| Tunnel drops or the server is unreachable | Kill switch stays; protected traffic dropped; status shows the failed stage; automatic reconnect |
| Server identity does not match | Connection refused; no fallback; clear error; kill switch stays |
| DNS through the tunnel fails | DNS stage shows failure; no fallback to underlay DNS |
| Network change (Wi-Fi ↔ mobile, new DHCP lease) | Rules stay; tunnel re-established; no gap (NP-E4) |
| Sleep and wake | Rules stay; reconnect after wake; no traffic before the rules are verified |
| Septuvo service crash | Kernel keeps the rules (NP-E5); service repairs on restart |
| Update of Septuvo | Rules stay in place during the update; the new version takes over the existing rules |
| User closes the app window | Tunnel and rules stay (D-019) |
| User explicitly disconnects | Rules removed and normal networking restored, unless always-on is enabled (Q2, Q4) |
| Boot before the service starts | Unprotected unless always-on is enabled, which blocks from boot (Q4) |
| Uninstall | All Septuvo routes, rules and DNS changes removed; verified, not assumed |

## 10. Not decided here

Protocol behaviour (handshake, keepalives, roaming, MTU) belongs to M2. Gateway address mapping for overlaps is a later option. Per-application split tunnelling is out of version 1.

## 11. Owner questions (this document)

Full explanations, options and trade-offs: [M1-owner-questions.md](../reviews/M1-owner-questions.md). Nothing here is decided until the owner answers.

| Q | Question | Recommendation |
| --- | --- | --- |
| Q1 | Captive portals (hotel or café login pages) | A user-started, time-limited (at most 5 minutes) captive-portal mode that lets web traffic out directly with a clear warning, then re-blocks. No permanent bypass. |
| Q2 | When the user explicitly disconnects, should blocking stay? | No: explicit disconnect restores normal networking. Any failure keeps blocking. |
| Q3 | Local discovery (mDNS, `.local`, casting, printers) | Blocked by default in version 1; NAS reached by address or a configured name. Revisit later. |
| Q4 | Always-on mode that blocks from boot | Offered as a setting, off by default (it can lock a new user out of the internet). |
| Q5 | Overlapping home and local subnets | The tunnel wins while connected (NP-S5); address mapping considered later. |
| Q6 | Traffic between the user's own enrolled devices | Off by default; the administrator can allow it. |
| Q13 | Default tunnel address range | A random `/24` inside `10.0.0.0/8` and a random IPv6 ULA `/64` (RFC 4193), picked per server at setup to avoid collisions; configurable. |
