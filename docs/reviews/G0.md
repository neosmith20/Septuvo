# G0 — Design baseline: evidence package (M0-03)

**Purpose:** give the owner one document to decide gate **G0** (design baseline). Approved by the work order [`docs/work-orders/M0-03.md`](../work-orders/M0-03.md) ([`APPROVED WORK ORDER M0-03`](https://github.com/neosmith20/Septuvo/pull/24#issuecomment-6162805811)).
**Prepared:** 2026-10-14 (UTC), against `main` @ `527f62b`.
**Decision:** the owner alone decides, by commenting `GATE G0 PASSED` or `GATE G0 FAILED` on this document's pull request (D-025).

**What G0 means.** The product scope, decisions, open questions and acceptance criteria are written down and agreed, so requirements work (M1) and the non-crypto Rust track (N1) can start.
**What G0 does not mean.** G0 approves no cryptography, no protocol design and no security claim. No SVP handshake, packet format, key handling or tunnel code is allowed until **G1** (qualified outside review plus owner approval). Anything not yet known is marked **OPEN** below rather than assumed.

## 1. Product scope

**Products (D-001):** Septuvo (company and brand), Septuvo VPN (apps), Septuvo Protocol (SVP), Septuvo Server (gateway).

**Version 1 user journeys (D-027):**

| Journey | What the user gets | Where it is specified |
| --- | --- | --- |
| A — Home network from anywhere | Reach the home network (for example a NAS or media server) securely from any network, through the user's own Septuvo Server | M1-02 |
| B — Untrusted Wi-Fi | All traffic leaves through the user's own server when on hotel, café or other untrusted Wi-Fi; nothing leaks if the tunnel drops | M1-02 |

**Baseline requirements already decided:** IPv4/IPv6 Layer 3, no Layer 2 bridge (D-003); an original, openly documented UDP protocol, not a fork (D-004); Rust for all Septuvo-owned security logic, with small listed OS glue only where required (D-005); every network untrusted, fail closed, LAN access only by explicit policy (D-006); standalone use with no account, cloud or Septuvo-run service (D-007); signed installers, no compiling by users (D-008); no mandatory telemetry (D-017); honest four-stage status — adapter, authenticated peer, reachability, DNS (D-020).

**Non-goals for version 1:**

- small-business site-to-site networks and multi-tenant provider service (D-027) — later milestones (M9), behind G4;
- Layer 2 bridging (D-003);
- a mandatory relay, coordination service or Septuvo cloud (D-007);
- anonymity from the server operator, hiding traffic timing or sizes, or protection of an already compromised device (SECURITY_MODEL "Out of scope");
- platforms other than Linux before the Linux lab works (D-014 order: Linux → Windows → macOS → Android → iOS);
- any performance, capacity or security claim that has not been measured or reviewed (D-009, D-018).

## 6. Change control

- **Every change goes through a pull request** on a task branch. Agents push task branches only; they never push to or merge into `main`, and never change repository settings (D-023).
- **Ruleset "Septuvo — protect main"** (active, empty bypass list): pull request required, required check `repository-integrity` (branch must be up to date), no force-push or deletion, linear history (squash merge). Details: [GITHUB_SECURITY_SETUP.md](../security/GITHUB_SECURITY_SETUP.md).
- **Owner decisions are exact comments** on the task's issue or pull request (D-025): `APPROVED WORK ORDER <ID>`, `ACCEPTED <ID>`, `REJECTED <ID>`, `GATE <Gn> PASSED/FAILED`. A milestone ID approves or accepts the whole milestone (D-030). [STATUS.md](../STATUS.md) mirrors them, and `scripts/verify_ledger.py` checks every mirrored row against GitHub in CI.
- **Automated scanning:** secret scanning with push protection, Dependabot alerts and updates, private vulnerability reporting, CodeQL (Actions, Python, Rust).
- **OpenSSF Scorecard** (added by the owner in [PR #23](https://github.com/neosmith20/Septuvo/pull/23)): runs on pushes to `main`, on ruleset changes and weekly, and publishes results to the public OpenSSF service. Note: its last step uses `github/codeql-action/upload-sarif@v3` by tag rather than by full commit SHA; pinning it is a small hygiene follow-up for the owner to authorize.
- **New Rust CI (N1-01)** becomes a required check only if the owner adds it to the ruleset.
- **Procedural limit:** agents and owner share one GitHub account, so these controls catch mistakes but cannot stop a dishonest agent (D-023, D-025). The owner's review of each pull request is the final control.

## 7. Outside-reviewer plan (for G1)

**When:** during M2, once there is a written SVP specification at a fixed commit. A reviewer cannot review a protocol that has not been written yet, so no search happens before then.

**What the reviewer must cover:** every item of the [protocol review checklist](../PROTOCOL_REVIEW_CHECKLIST.md):

| Item | Topic | Item | Topic |
| --- | --- | --- | --- |
| P-01 | Threat and trust model | P-08 | Replay and state |
| P-02 | Version and wire format | P-09 | Key rotation and lifetime |
| P-03 | Identity and enrollment | P-10 | MTU and fragmentation |
| P-04 | Hybrid handshake | P-11 | DoS and resource protection |
| P-05 | Transcript and KDF | P-12 | Error and failure behavior |
| P-06 | Cipher suites and downgrade | P-13 | Test fixtures and conformance plan (D-021) |
| P-07 | Packet numbers and nonces | P-14 | Protocol analysis and residual risk |

**Who qualifies:** a person or team with published or verifiable experience analysing cryptographic protocols; independent of the project (not an agent, not the owner); willing to deliver a written report that names the exact commit reviewed, lists findings with severity and states residual risk. A formal model of the handshake (for example with Tamarin or ProVerif) is desirable but not mandatory.

**Search plan (carried out in M2-05):**

1. **Prepare a review package:** the specification at a fixed commit, the threat model, the scope (the P-items above), and a short list of the questions we most need answered.
2. **Apply to free or subsidized programs** (eligibility, availability and waiting times change and are checked at that time; none has been contacted yet):
   - [Open Technology Fund](https://www.opentech.fund/) Security Lab (formerly Red Team Lab): audits for open-source internet-freedom and privacy tools;
   - [OSTIF](https://ostif.org/) (Open Source Technology Improvement Fund): arranges and funds security audits of open-source projects;
   - [NLnet Foundation](https://nlnet.nl/) NGI Zero: grants that include security review support; eligibility rules must be checked.
3. **Ask academic groups:** university applied-cryptography or protocol-verification groups, for example as a student project with faculty supervision. Usually free but slower; the supervisor's qualification counts, not the student's alone.
4. **Get paid quotes as a fallback:** budget **OPEN** (question 12).
5. **Public feedback** (posting the specification for comment) is welcome but **never replaces** a qualified review.

If no qualified reviewer is available, G1 stays **BLOCKED**. Track N1 and specification work can continue, but no cryptographic or protocol code is written.

## 8. Known risks

| Risk | Effect | Mitigation |
| --- | --- | --- |
| No qualified outside reviewer found, or long queues | G1 delayed; no tunnel code | Start the search as soon as the M2 draft exists; several free channels; keep N1 moving meanwhile |
| A single human reviewer (the owner), who is not a cryptographer | Mistakes in agent work could be missed | Small pull requests, automated checks, plain-language summaries, outside review at G1 and G3 |
| Agents share the owner's GitHub account | Controls are procedural (D-023) | Ruleset, required checks, owner merges; revisit before collaborators or G3 |
| AI agents may invent or overstate | Wrong specs or claims | Red lines in AGENTS.md; candidates labelled; evidence must be real command output; reviewer at G1 |
| Candidate cryptography may change after M2-01 analysis | Rework of requirements | Candidates stay candidates; changes recorded as new D-IDs |
| GitHub-hosted runners differ from the Ubuntu VM lab | N1-03 results may not carry over exactly | Same Ubuntu 24.04 base; repeat the lab tests on the VM stage before G2 |
| OS glue may be larger than "small" on some platforms | D-005 inventory grows | Feasibility in M1-04; every exception listed |
| Public repository while the name is not cleared (D-016) | Possible naming conflict later | No ™/® symbols or rights claims until cleared |
| One workflow step referenced by tag, not SHA (Scorecard) | Small supply-chain exposure | Owner-authorized pin (section 6) |
