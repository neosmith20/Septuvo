# Work order — N4: Septuvo VPN desktop application for Linux (milestone)

**Status:** proposed. **Authorization (D-031, category B):** the owner's merge of the pull request that adds this file authorizes N4-01 to N4-07, in order, **and the owner decisions listed under "Decisions made by this work order"**. After each task's pull request is merged, the agent continues with the next one without a new go-ahead (D-034).

- **Task ID / milestone:** N4 (covers N4-01 to N4-07 in [TASK_CATALOG.md](../TASK_CATALOG.md))
- **Predecessor:** N3 accepted (PRs #62–#66, and H-018 in #65)
- **Required gate:** G0 passed (#25). **G1 is not required, because nothing in N4 is cryptographic** (D-029). G1 stays **NOT PASSED** and continues to block all protocol and cryptographic code.
- **Objective:** the first real Septuvo VPN desktop application, **100% Rust (D-005)**, built on the service from N2–N3:
  - a modern, responsive Linux window and a tray icon;
  - status monitoring, connection controls, configuration management and clear diagnostics;
  - all reusing the existing Rust components rather than duplicating them.
- **Relationship to the roadmap:** this is an **early, lab-only Linux slice of M7-01/M7-02** (desktop application, close-to-tray behaviour). M7 itself is unchanged: other platforms, signed packages and a real tunnel's status come later.

## The Rust-only rule (D-005)

**Septuvo VPN and Septuvo Server are 100% Rust, without exceptions.** That covers this app, its UI, the service, the installer and every bundled application-level dependency.
- **Allowed:** using the operating system's own interfaces (kernel, C library, display server, keyboard layouts, graphics drivers, desktop services over D-Bus).
- **Not allowed:** Rust bindings around a C/C++ application framework (**GTK and libadwaita are rejected**), and bundled non-Rust engines (Skia, WebKit and the like).
- **Evidence for the chosen stack:** [rust-gui-evaluation.md](../reviews/rust-gui-evaluation.md). It audits the full dependency tree, builds the binary and inspects it.
- **No exceptions may be added during N4.** If any task seems to need non-Rust code, the agent stops and reports.

## The G1 boundary (unchanged)

**Not allowed:**
- an SVP handshake, packet encryption or wire encoding;
- key generation or management;
- usable invitations or enrollment;
- functional protocol transport;
- any cryptography crate in Septuvo's code.

**What the app shows before G1:**
- the honest pre-G1 state: **never "connected"**, because peer authentication always fails (D-020);
- enrollment and server-identity screens as **disabled placeholders**, labelled "available after the G1 security review".

**Still lab-only.** The app talks to the same lab-mode service, which runs only in its lab network namespace (N3-01).

## Architecture

```text
 Septuvo VPN (desktop app, unprivileged user)        septuvod (root, lab namespace)
 ┌─────────────────────────────────────────────┐     ┌──────────────────────────────┐
 │ egui/eframe window + AccessKit, ksni tray   │     │ kill switch, DNS, captive     │
 │ view model (plain Rust, unit-tested)        │     │ portal (N2–N3), config apply  │
 │ septuvo-ipc · status model (septuvo-cli)    │◀───▶│ and diagnostics (new in N4)   │
 │ septuvo-config (validation only)            │ IPC │ septuvo-config (authoritative)│
 └─────────────────────────────────────────────┘     └──────────────────────────────┘
   all Rust ─────▶ OS interfaces only: display server, keyboard layouts,
                   OpenGL driver, D-Bus (tray host, notifications, portals, AT-SPI)
```

**Principles:**
- **One source of truth.** The app shows what the service reports, through the same `septuvo-ipc` client and the same four-stage status model as `septuvo status` / `septuvo watch`. A lost service is shown at once, never as the last known state (as in N3-04).
- **Least privilege.** The app runs as the user and **refuses to run as root**. Changes go through the service's control socket, so the user must be in the `septuvo` group.
  - There is **no `sudo`, `pkexec` or polkit** prompt in N4.
  - Without membership the app says exactly how to get it.
- **The service stays authoritative.** The app validates configuration with `septuvo-config` for instant feedback, but the service validates again, writes and applies it. The app never writes `/etc/septuvo`.
- **Closing is not disconnecting (D-019).** Closing the window or quitting the tray only stops the *viewer*. Only a deliberate disconnect lifts protection (Q2).
- **Untrusted input everywhere.** Service responses, configuration and diagnostics are shown **as plain text**. Nothing from outside the app is ever interpreted as markup, links or commands.

### N4-02 — Status and monitoring

- **Outputs:** `desktop/`, `docs/build/desktop.md`, and moving shared helpers into `septuvo-cli` (Apache-2.0) where both the CLI and the app need them, rather than copying.
- **Work:** the main window's status page, refreshed every 1–2 s over the **status socket**. It shows:
  - the four checks, each with plain-language help;
  - the service state, kill switch, DNS policy and resolver file;
  - the captive-portal window (countdown, warning, helper account, windows left);
  - a prominent **service lost** banner.

  The overall line uses the shared status model: **"Connected" only when all four checks pass**.
- **Responsive and accessible:**
  - an adaptive layout from narrow (360 px) to wide, with explicit width breakpoints;
  - every state has text, not colour alone;
  - accessible names and roles for every status element (AccessKit).
- **Acceptance:**
  - view-model tests for every state (as N3-04, including the 81 combinations);
  - **UI tests that query the accessibility tree** for each state;
  - a **namespace lab case**: the app runs against the lab service while the lab connects, opens a captive window, disconnects and kills the service, and the UI follows each change (read through the accessibility tree).

### N4-03 — Tray integration and notifications

- **Outputs:** `desktop/`, `docs/build/desktop.md`.
- **Work:** a StatusNotifierItem tray icon (`ksni`).
  - **Icon and tooltip by state:** not running or lost, disconnected, blocking, captive window open. **No "protected" or "connected" icon exists before G1.**
  - **Menu:** open window, connect, disconnect, captive-portal window, quit viewer.
  - **Desktop notifications** (`notify-rust`, zbus): service lost, captive window opened and about to end, connect or disconnect failed.
  - **Closing:** closing the window keeps the tray running (D-019).
  - **Without a tray host:** the app detects this and keeps a normal window.
- **Acceptance:**
  - unit tests mapping every state to icon, tooltip and menu;
  - a CI test on a private D-Bus session with a test tray host and notification server, checking registration, state changes and notifications.

### N4-04 — Connection controls and permissions

- **Outputs:** `desktop/`, `docs/build/desktop.md`, `tests/lab/namespaces/`.
- **Work:**
  - **Connect, disconnect and captive-portal window** (minutes, explicit network-DNS option with its warning) through the **control socket**, with the same IPC commands as the CLI.
  - **Disconnect needs a confirmation** that says what happens (rules removed, resolver file restored).
  - **Without control-group membership,** the controls are disabled with an explanation and the exact command to join the group. There is never an elevation prompt (N4-D7).
  - **Errors from the service are shown as plain text.**
- **Acceptance:**
  - view-model tests (enabled or disabled states, confirmation, error display);
  - a lab case: a group member connects, opens a captive window and disconnects through the app; a non-member sees disabled controls and the service state never changes.

### N4-05 — Configuration management

- **Outputs:** `crates/septuvo-ipc/`, `crates/septuvo-daemon/`, `crates/septuvo-config/` (if needed), `desktop/`, `tests/lab/namespaces/`, `fuzz/`, `docs/build/daemon.md`, `docs/build/desktop.md`.
- **New service commands:**
  - `CONFIG-GET`, on the status socket: the current device configuration as text, **bounded to the parser's 64 KiB limit**.
  - `CONFIG-APPLY`, on the control socket only, with a length-prefixed body of at most 64 KiB. This is the protocol's one exception to the 64-byte request limit, specified and fuzzed. The service then:
    1. validates with `septuvo-config`;
    2. keeps a backup;
    3. writes atomically;
    4. if connected, **replaces the kill switch atomically with the new rules**.

    **Any failure leaves the previous file and the previous rules in place (fail closed).**
- **App:** a settings page for the routing mode, the `direct`, `tunnel` and `block` lists, the DNS resolvers and LAN exceptions, the interface and MTU, and "always on".
  - It shows validation errors inline, at the field, using `septuvo-config`'s messages and positions.
  - Before applying, it shows a **diff and a plain-language summary** of what will change.
- **Acceptance:**
  - **IPC tests** and **new fuzz targets** (standard library and cargo-fuzz) for the framed request;
  - engine tests for apply, rejection, rollback, and apply while connected;
  - a lab case: applying a change while connected switches the rules atomically, with no window where traffic leaks; a bad configuration changes nothing;
  - app view-model and UI tests.

### N4-06 — Diagnostics

- **Outputs:** `crates/septuvo-ipc/`, `crates/septuvo-daemon/`, `crates/septuvo-cli/` (new `septuvo diagnose`), `desktop/`, `tests/lab/namespaces/`, `fuzz/`, `docs/build/`.
- **New service command:** `DIAGNOSE`, read-only, on the status socket. It returns bounded facts:
  - service version and mode, lab namespace, uptime;
  - kill-switch table present, its rule count and a short summary (no raw dump);
  - resolver file state, captive-helper account configured, recent service events (counts and times only).
- **Client-side checks** (CLI and app):
  - the service is reachable;
  - the user is in the control group, and whether the login session already knows it;
  - socket permissions;
  - versions match.
- **Every finding comes with a plain-language "what this means" and "what to do".**
- **`septuvo diagnose` and the app's diagnostics page** show the same findings and can **save a text report the user chooses where to put** (the portal file chooser, N4-D3).
  - **Nothing is sent anywhere** (no telemetry, S-13).
  - The report lists exactly what it contains, and leaves out user names, home paths and anything not needed.
- **Acceptance:**
  - unit tests for every finding;
  - fuzzing of the new response;
  - a lab case with deliberate faults: service stopped, user not in the group, rules removed behind the service's back. The right finding and advice must appear for each.

### N4-07 — Rust installer, packaging, accessibility and the user guide

- **Outputs:** a Rust installer replacing `packaging/linux/install.sh` and `uninstall.sh` (N4-D8); `packaging/linux/` (desktop entry, icons, autostart entry); `tests/lab/install/`; `desktop/`; `docs/build/install.md`; `docs/build/desktop.md`; `docs/user/linux-desktop.md` (new); `docs/spec/rust-inventory.md`.
- **Installer:** `septuvo-setup install|uninstall` in Rust. It does the same work as the N3-01 scripts (file list, sysusers, tmpfiles, units, keep or purge configuration, leave no rules behind) plus the app:
  - a `.desktop` file;
  - the brand icons at the standard sizes;
  - a tray autostart entry, off by default.

  **The shell scripts are removed.**
- **Accessibility pass:**
  - keyboard-only operation of every function;
  - screen-reader names and roles checked through the accessibility tree;
  - contrast of the brand colours checked in light and dark themes;
  - text scaling.
- **Responsiveness pass:** usable from 360 px wide, with no frozen UI. Service calls run off the UI thread, with time-outs.
- **A user guide for non-technical users,** with screenshots taken in CI.
- **Acceptance:**
  - the install test passes against the Rust installer (staged file list, real install and uninstall on the runner, nothing left behind);
  - `rust-inventory.md` shows no shipped non-Rust code;
  - an accessibility checklist recorded with evidence;
  - the guide reviewed by the owner in the PR.

## Dependencies, toolchain, environments

- **The service and libraries** (`crates/`) stay **standard library only**, with no `unsafe` and the pinned toolchain, as in N1–N3.
- **`desktop/`** may use **only** the Rust crates approved in N4-01's review (N4-D1 to N4-D3 and their pinned transitive dependencies), enforced by the Rust-only gate. **No `unsafe` in Septuvo's own app code.**

## Risks

| Risk | Handling |
| --- | --- |
| A non-Rust dependency slips in | The Rust-only gate in CI over the full Linux dependency tree; the review before every addition; exact pins |
| The app is mistaken for a working VPN | Never "connected" or a "protected" icon before G1; "development preview, no tunnel" on the main page and About; enrollment screens disabled |
| **The egui look is not polished enough** | A Septuvo theme from the brand tokens and Inter; **owner approval of prototype screenshots in N4-01** before more is built; a polish pass in N4-07 |
| No GPU (VMs, old machines) | The glow renderer runs on Mesa's software OpenGL (an OS driver) |
| Complex-script text (for example Arabic) | English-first UI; re-evaluate before localization |
| A GUI widens the attack surface | Unprivileged, refuses root; read-only status socket for viewing; control only through the existing socket and group; plain text only; config applied only by the service, after its own validation |
| Config apply leaves a gap in protection | Atomic file write and atomic nft replacement; failure keeps the old file and rules; lab test while connected |
| No tray on GNOME | Works as a window; explains the AppIndicator extension |
| UI tests are flaky in CI | Logic in a plain-Rust view model with unit tests; UI tests query the accessibility tree, not pixels; screenshots only for review |
| Scope creep (other platforms, polkit, enrollment, auto-update) | Out of scope below; stop and ask |

## Not in N4

- Windows, macOS and mobile apps (M7). Their open Rust-only questions are recorded in [rust-inventory.md](../spec/rust-inventory.md).

- Enrollment, server identity, invitations and anything needing SVP (after G1).
- Signed packages, auto-update and distribution (G3).
- A captive-portal sign-in browser (phase 2 of N3-02, which needs the TLS decision).
