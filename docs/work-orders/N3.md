# Work order — N3: Installable lab service, captive portals, fuzzing and live status (milestone)

**Status:** proposed. **Authorization (D-031, category B):** the owner's merge of the pull request that adds this file authorizes N3-01 to N3-04, in that order. After each task's pull request is merged, the agent continues with the next one without a new go-ahead (D-034).

- **Task ID / milestone:** N3 (covers N3-01 to N3-04 in [TASK_CATALOG.md](../TASK_CATALOG.md))
- **Predecessor:** N2 accepted (PRs #56–#59)
- **Required gate:** G0 passed (#25). **G1 is not required, because nothing in N3 is cryptographic** (D-029). G1 stays **NOT PASSED** and continues to block all protocol and cryptographic code.
- **Objective:** turn the N2 foundation into something a person can install, use on a hotel network and trust under hostile input:
  - an installable, hardened Linux service, still lab-only;
  - the captive-portal mode the owner decided in Q1;
  - systematic fuzzing of every parser;
  - a live status view.

## The G1 boundary (unchanged from N2)

**Not allowed:**
- an SVP handshake, packet encryption or wire encoding;
- key generation or management;
- usable invitations or enrollment;
- functional protocol transport;
- any cryptography crate.

Placeholders keep returning errors, and status never reports "connected" (D-020).

**Still lab-only.** The service keeps its N2-02 guard: it runs only inside a named lab network namespace and never changes the host's own firewall or DNS. The installer installs it to run *in* such a namespace (N3-01). Running it on a real network outside a lab namespace is **not** part of N3 and needs its own work order and risk review.

## Dependencies, toolchain, environments

- **Code:** standard library only, no `unsafe`, pinned toolchain, exactly as in N1 and N2. No third-party crate may be added.
- **System tools:** the installer may use the system tools a Linux system already has: `systemd`, `systemd-sysusers`, `systemd-tmpfiles`, `ip`, `nft`, `install`.
- **Real installs** happen only on disposable CI runners or an owner lab VM. Everything else installs into a staging directory (`DESTDIR`) and is inspected there.

## Tasks

### N3-01 — Installer and service setup (Linux, lab mode)

- **Outputs:**
  - `packaging/linux/`, containing:
    - `septuvod.service`;
    - `septuvo-lab-netns.service`;
    - `septuvo.sysusers` and `septuvo.tmpfiles`;
    - `septuvod.toml` and `septuvo.toml` templates;
    - `install.sh` and `uninstall.sh`;
  - `tests/lab/install/`;
  - `.github/workflows/rust.yml`;
  - `docs/build/install.md`.
- **What gets installed:**
  - binaries in `/usr/libexec/septuvo/septuvod`, `/usr/bin/septuvo` and `/usr/sbin/septuvo-server`;
  - configuration in `/etc/septuvo/`, never overwritten if it already exists;
  - the `septuvo` control group, via sysusers;
  - `/run/septuvo`, via tmpfiles.
- **`septuvo-lab-netns.service`** creates the named lab namespace (`septuvo-lab`). **`septuvod.service`** joins it (`NetworkNamespacePath=/run/netns/septuvo-lab`) and runs with systemd hardening:
  - `CapabilityBoundingSet=CAP_NET_ADMIN CAP_CHOWN CAP_FOWNER`;
  - `NoNewPrivileges=yes`;
  - `ProtectSystem=strict` with only the needed paths writable;
  - `ProtectHome=yes`, `PrivateTmp=yes`;
  - restricted address families;
  - `SystemCallArchitectures=native`.

  The service's N2-02 guard still applies on top.
- **`install.sh`:**
  - takes `--prefix` and `DESTDIR`;
  - installs prebuilt release binaries; the user never compiles. Building those binaries in CI is part of this task, publishing them is not;
  - is idempotent, refuses to run without root unless `DESTDIR` is set, and changes nothing outside the listed paths.
- **`uninstall.sh` removes everything the installer added and leaves no rules behind:**
  - it runs `septuvo disconnect` first (restoring the resolver file), removes the Septuvo nft table in the lab namespace, stops and removes the units, and removes the files and the group;
  - it keeps `/etc/septuvo/` unless `--purge` is given, and says so.
- **Acceptance:**
  - `systemd-analyze verify` passes for every unit;
  - a `DESTDIR` install produces exactly the expected file list, modes and owners;
  - **in CI, a real install on the disposable runner:** the service starts in the lab namespace, `septuvo status` works for a normal user, connect and disconnect work for a group member, and stopping the service keeps blocking (Q2);
  - uninstall leaves no files, units, group, namespace or nft table behind (checked by listing);
  - re-running the installer changes nothing.

### N3-02 — Captive-portal mode (owner decision Q1), revised

> **Revised after the owner's review of PR #63 (2026-10-17).** The first version let *every* program use TCP 80/443 and the network's DNS outside the tunnel during the window. The owner rejected that: Septuvo is zero-trust, so ordinary applications must stay protected, network-provided DNS and data are untrusted, and HTTPS verification must never be weakened. The owner's seven requirements are the scope below. Design, evaluation and phased plan: [captive-portal.md](../build/captive-portal.md).

- **Outputs:**
  - `crates/septuvo-policy/` (renderer);
  - `crates/septuvo-daemon/`;
  - `crates/septuvo-ipc/`, with new command `CAPTIVE N [NETWORK-DNS]`;
  - `crates/septuvo-cli/`, with `septuvo captive-portal [--minutes N] [--network-dns]`;
  - `packaging/linux/` (the dedicated helper account, template setting, uninstall);
  - `tests/lab/namespaces/`, `tests/lab/install/`;
  - `docs/build/captive-portal.md`, `daemon.md`, `install.md`.
- **Behaviour** (network-policies NP-U5, Q1, threats R-09):
  - **Requirement 1, no unrestricted bypass.**
    - The window applies **only to one dedicated helper account** (`septuvo-portal`), matched by the kernel (`meta skuid`). Every other program keeps exactly the kill-switch rules.
    - The helper is isolated at all times: never through the tunnel, never to anything the policy names, never to the server endpoints.
    - During the window it may use TCP 80/443 outside the tunnel, and nothing else.
  - **Requirement 2, trusted DNS first.** By default the helper has **no plain DNS at all**: it must use encrypted DNS over HTTPS (for example Cloudflare) on its web ports. A Septuvo DoH client needs a TLS library, so it is deferred to phase 2 (owner decisions D-015 and the G1 boundary).
  - **Requirement 3, RFC 8910 / 8908** are evaluated in the design note. Implementing them needs DHCP/RA access and an HTTPS client, so they are deferred to phase 2. Network-provided data is treated as untrusted throughout.
  - **Requirement 4, no automatic fallback.**
    - The network's own DNS is opened **only** with an explicit `--network-dns` for that one window, and **only for the helper**.
    - The resolver file is never changed, so system-wide DNS never moves to the network's resolver.
  - **Requirement 5, HTTPS verification.**
    - Nothing in Septuvo touches certificates.
    - Legacy portals that cannot be supported safely are listed in the design note.
  - **Requirement 6, kernel-enforced expiry.**
    - The window lives in nftables **sets with a kernel-enforced timeout** of at most 5 minutes, so it closes on time even if the service dies.
    - Asking again restarts from now and never adds up.
    - There are **at most 3 windows per connection**, each one logged.
    - Disconnect or reconnect ends it at once, and nothing starts it automatically.
  - Only a control-group member can open a window, only while connected, and only if a helper account is configured (never root). A warning is shown when it opens and in status.
- **Acceptance (requirement 7):**
  - renderer tests prove the rules for ordinary programs are identical with and without captive-portal mode;
  - **namespace lab cases:**
    - ordinary programs (root and another user) cannot use the window for web traffic, DoH or DNS;
    - the helper reaches the sign-in page, HTTPS and the DoH resolver, but not QUIC, other ports, DNS over TLS, the tunnel, policy-listed hosts or the endpoint;
    - the network's DNS works only with `--network-dns`, only for the helper;
    - **malicious DNS answers** pointing behind the tunnel or at blocked hosts redirect nothing, and ordinary lookups never reach the network's resolver;
    - the resolver file is unchanged;
    - a service killed mid-window still re-blocks on time;
    - refusals: non-member, not connected, no helper, root as helper, a fourth window;
    - status shows the remaining time and the warning;
  - the real install creates and removes the helper account.

### N3-03 — Fuzz testing (standard library only)

- **Outputs:**
  - fuzz tests in `crates/septuvo-config/`, `crates/septuvo-ipc/`, `crates/septuvo-server/`, `crates/septuvo-policy/` and `crates/septuvo-daemon/`;
  - `.github/workflows/fuzz.yml`;
  - `docs/build/fuzzing.md`.
- **Method:**
  - a small, deterministic, seeded input generator (test code only, never used for anything security-related) that produces random, mutated and structure-aware inputs;
  - run against every parser: the TOML subset, the device and server schemas, the policy file format, IPC requests and responses, device records and the daemon's settings;
  - **properties checked:**
    - no panic;
    - output bounded;
    - "valid" results re-encode and re-parse identically where a format round-trips;
    - rejecting never changes state.
- **Runs:**
  - a short run in every pull request;
  - a long run in a scheduled weekly CI job and on demand. The seed of any failure is printed, so it can be replayed and added as a regression test.
- **Not included:** coverage-guided fuzzing with `cargo-fuzz` / libFuzzer. It needs a third-party crate and a nightly toolchain, so it would be a separate owner decision on dependencies (D-015). The document says how to add it later.
- **Acceptance:** every parser has a fuzz target; the short run passes in CI; a long run of at least 30 minutes per target has completed in CI, with its result recorded; any bug found is fixed with a regression test in the same pull request.

### N3-04 — Live status view

- **Outputs:**
  - `crates/septuvo-cli/`, with `septuvo watch`;
  - `docs/build/daemon.md`.
- **What:**
  - `septuvo watch [--interval S]` shows the four checks (D-020), the service state, the kill switch, the DNS policy, the resolver file and the captive-portal countdown, refreshed in place in the terminal, until it is stopped;
  - standard library only (ANSI terminal output, plain-text fallback when output is not a terminal);
  - read-only, over the status socket;
  - **it never shows "connected" unless all four checks pass**, and a lost connection to the service is shown at once, not as the last known state.
- **Why not a desktop or tray app in N3:** graphical toolkits (GTK, Qt, system tray libraries) are third-party code with native bindings. Adding one is an owner decision on dependencies (D-015) and on licensing, so it is proposed for a later work order. `septuvo watch` uses the same status interface a graphical app would use.
- **Acceptance:**
  - unit tests for rendering every state, including "service lost";
  - a namespace lab case runs `septuvo watch` for a few refreshes while connect, disconnect and captive-portal mode change, and checks that the output followed each change.

## Risks

| Risk | Handling |
| --- | --- |
| An installed service mistaken for a working VPN | Installer, unit files and status all say lab preview, no tunnel; status never shows "connected"; the service runs only in the lab namespace |
| Installer damages a system | `DESTDIR` staging by default in tests; real installs only on disposable runners; idempotent; uninstall verified to leave nothing |
| Captive-portal mode becomes a permanent bypass, or a bypass for ordinary programs | Helper account only (kernel `skuid` match); kernel-enforced timeout, a 5-minute cap, no adding up, at most 3 windows per connection, ends on disconnect, never automatic; lab test kills the service mid-window and proves ordinary programs stay blocked |
| Fuzzing slows CI | Short runs per pull request; long runs scheduled |
| Scope creep toward a GUI or real-network deployment | Out of scope above; stop and ask |
