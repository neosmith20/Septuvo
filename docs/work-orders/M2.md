## Rules for writing a protocol without inventing cryptography

1. **Assemble, don't invent.** SVP is built only from published constructions with independent analysis:
   - standardized primitives (for example ML-KEM, ML-DSA, X25519, HKDF, AES-GCM, ChaCha20-Poly1305);
   - analysed handshake patterns;
   - analysed hybrid combiners.

   Each is used **exactly as specified** by its source, with a citation.
2. **Everything new is flagged.** Any glue that is not taken verbatim from a reviewed source is marked **BLOCKED — needs G1 review** in the specification, with the reason. Examples: a label string, an encoding choice, an ordering, a deviation. It is never presented as settled.
3. **No borrowing without analysis.** Following WireGuard, TLS or Noise is allowed only with a written note on what changes and why the source's analysis still applies (AGENTS.md).
4. **Candidates stay candidates.** The specification names a *proposed* suite. D-010, D-011, D-012 and D-024 become decided only through the G1 review and the owner's explicit decision (category C).
5. **Documentation only.** No code, no computed test vectors, no executable packet format, no live networking (D-021, D-029). N1 code is not extended into protocol work.

## The outside review (M2-05)

The owner and the reviewer drive this part; the agent prepares and supports.

- **The agent prepares:**
  - the review package: the specification at a fixed commit, the threat model, scope (P-01 to P-14) and the top questions;
  - short outreach messages for the owner to send, to the free and low-cost options in [G0.md](../reviews/G0.md) section 7: OTF Security Lab, OSTIF, NLnet NGI Zero, and university applied-cryptography groups. The agent checks each program's current eligibility first.
- **The owner sends the messages and chooses the reviewer.** Agents never contact outside parties.
- **Responding to findings:** the agent answers in small specification revisions, each a pull request. A material change re-opens review of that part.
- **G1** is decided only by the owner's exact comment `GATE G1 PASSED` (or `FAILED`), after a qualified reviewer's written sign-off on the exact commit. If no reviewer is available, M2-05 stays **BLOCKED** and **no protocol or cryptographic code is written**.

## Delivery

- One pull request per task (M2-01, M2-02, M2-03, M2-04), in order, each with commit subjects `docs(M2-0x): ...`. The owner's merge accepts each one.
- Technical choices the owner must make are presented as short questions with recommendations, as in M1.

## Acceptance

- The task card criteria in [TASK_CATALOG.md](../TASK_CATALOG.md).
- Every P-01 to P-14 item answered or marked OPEN.
- Every non-standard element marked BLOCKED.
- Both repository checks and the licensing check pass.

## Out of scope

- Any code: Rust, scripts or generators for protocol messages.
- Computed vectors.
- Choosing cryptography on the owner's behalf.
- Changes to N1 code.
- Contacting reviewers.
- M3 implementation.

## Risks

| Risk | Handling |
| --- | --- |
| No qualified reviewer accepts, or queues are long | Start the search when M2-02 is drafted, not at the end; several channels in parallel. G1 waits; nothing unsafe proceeds |
| A specification that looks complete hides an unreviewed construction | Rule 2: everything non-standard is marked BLOCKED, and the reviewer gets that list first |
| Post-quantum library maturity in Rust | M2-01 records maturity and audits; dependency approval later follows D-015 |
| Scope creep into implementation | Documentation only; CI and review catch code changes |

**Stop point:** after M2-04, stop and hand over the review package. M2-05 proceeds at the reviewer's pace. Nothing beyond M2 starts without G1.
