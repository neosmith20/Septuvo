# Work order — N1: Non-crypto Rust foundation (milestone)

**Status:** proposed (H-006 pull request). Approve with `APPROVED WORK ORDER N1` on that pull request; the approved revision is this file at the pull request's head commit at that moment (D-030). Work starts only after `GATE G0 PASSED`.

- **Task ID / milestone**: N1 (covers N1-01, N1-02, N1-03, N1-04 in [TASK_CATALOG.md](../TASK_CATALOG.md))
- **Required gate**: G0 passed. G1 is **not** required because nothing here is cryptographic (D-029).
- **Objective**: the first real Septuvo code — a Rust workspace with CI, the routing/LAN-exception policy engine, a lab-tested kill switch and a CLI with an honest connection-status model.
- **In scope**: the outputs listed in the four N1 cards, plus mirroring owner decision comments in `docs/STATUS.md`.
- **Toolchain and dependencies**:
  - the current stable Rust release at implementation time, pinned in `rust-toolchain.toml` and recorded in the pull request;
  - **no third-party crates** (standard library only);
  - CI uses only `actions/checkout`, pinned to the full commit SHA already used in this repository, with read-only permissions;
  - the lab tests install the Ubuntu `nftables` and `iproute2` packages on the disposable GitHub-hosted runner only.
- **Lab rules**: root privileges only inside disposable runners or an owner lab VM; network namespaces only; no tunnel, no internet traffic, no change to any real host, router or firewall.
- **Out of scope**: SVP handshake, packet format, encryption, key handling, data tunnel, any cryptography crate, installers, Windows/macOS/mobile.
- **Delivery**: up to two pull requests (N1-01 + N1-02, then N1-03 + N1-04), one commit per task.
- **Acceptance criteria**: as in each card; CI green; a reviewer can see in the diff that no cryptography or tunnel code exists. Making the new Rust CI a required check stays an owner choice.
- **Stop point**: pull request(s) ready; the owner accepts the milestone with `ACCEPTED N1`. Nothing beyond N1 starts without a new work order.
